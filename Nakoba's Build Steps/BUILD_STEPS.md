## 1. Project File Inventory

### Root-level files

| File | What It Does | Why It Exists |
|---|---|---|
| `params.yaml` | Single source of truth for every hyperparameter: train/test split, Ridge α, Lasso α/iterations, voting weights, interval confidence, sweep alphas, MLflow experiment name. | Separating config from code means you can retune the model by editing one YAML file — no Python edits, no risk of breaking logic. DVC reads this file to decide which pipeline stages need re-running. |

| `requirements-mlops.txt` | MLOps tooling deps (MLflow, DVC, DagsHub, PyCaret). | Installed on the training/experiment workstation, NOT inside the Docker image. Separating them means the 500 MB PyCaret dependency tree never pollutes the ~200 MB API image. |

| `MLOPS_LAB.md` | Step-by-step Lab 5 walkthrough for learners. | Educational guide for the MLOps course module. |
| `.env.example` | Documents every environment variable. | Copy to `.env`, fill in values. `.env` is git-ignored so secrets never leak. |

| `Dockerfile` | Multi-stage Docker build: builder stage installs deps + downloads NLTK data; runtime stage is a minimal image with a non-root user. | Container packaging = the app runs the same everywhere (your laptop, AWS ECS, App Runner). Training                           Serving
──────────────────────────────     ──────────────────────────────────────────
mlops/train.py                     src/inference.py
↓                                  ↓

Splits 80/20 (seed=42)             For each POST /predict request:

## 3. How the VotingRegressor Works and Why It Was Chosen

### Architecture

```
PropertyInput (115 features)
        │
        ▼
┌───────────────────────────────────────────────────┐
│              VotingRegressor                      │
│                                                   │
│  ┌─────────────────┐  ┌──────────────────────┐   │
│  │ LinearRegression│  │  Ridge(alpha=10)      │   │
│  │ (no penalty)    │  │  (L2 regularisation)  │   │
│  └────────┬────────┘  └──────────┬───────────┘   │
│           │                      │                │
│  ┌────────┴──────────────────────┴───────────┐   │
│  │         Lasso(alpha=0.1)                  │   │
│  │         (L1 regularisation, sparse)       │   │
│  └───────────────────────────────────────────┘   │
│                      │                            │
│             Average (equal weights)               │
└───────────────────────────────────────────────────┘
        │
        ▼
   Predicted price (₹ lakhs)
```

### Why each model is included

| Sub-model | Strength | Role in the ensemble |
|---|---|---|
| **LinearRegression** | Unbiased on simple linear relationships; interpretable. | Provides an unregularised baseline that captures the raw linear trend. |
| **Ridge (α=10)** | L2 penalty shrinks all coefficients toward zero without eliminating any. | Handles multicollinearity in the 115-dimensional feature space (text features are correlated). Keeps all features active. |
| **Lasso (α=0.1)** | L1 penalty drives some coefficients exactly to zero. | Performs implicit feature selection — useful when many count-vectorizer columns are near-zero. |

### Why VotingRegressor over a single model

- **Variance reduction**: Averaging three models trained on the same data reduces the variance of the prediction compared to any single model.
- **Bias–variance trade-off**: Linear regression is low-bias but high-variance; Ridge and Lasso pull the variance down.
- **Simplicity + interpretability**: No boosting trees, no deep learning — the ensemble is easy to explain to stakeholders and runs in milliseconds.
- **Results**: Test R² = 0.852 (VotingRegressor) vs ≈0.83 for plain OLS — a tangible lift from the ensemble.

### Equal vs. weighted voting

`params.yaml` sets `voting.weights: null`, which means equal voting. You can assign weights (e.g. `[1, 2, 1]` to up-weight Ridge) and `dvc repro` will re-train automatically.

## 4. How the 95% Prediction Interval Is Computed

### Intuition

A single point estimate (e.g. ₹62 lakhs) is not very useful without a range. The prediction interval says: "the true price will fall inside [₹30 lakh, ₹93 lakh] 95% of the time."

### Mathematical derivation (`mlops/utils.py → compute_interval_estimate`)

**Step 1 — Compute training residuals**
```
residuals = y_train_true - y_train_predicted
```
These are the errors the model makes on its own training data.

**Step 2 — Estimate residual standard deviation**
```
σ = std(residuals)
```
The standard deviation of residuals is the "typical error" of the model.

**Step 3 — Find the z-score for the desired confidence level**
```
z = stats.norm.ppf(1 - (1 - 0.95) / 2)
  = stats.norm.ppf(0.975)
  ≈ 1.96
```
1.96 is the standard normal quantile corresponding to 95% coverage.

**Step 4 — Compute the margin**
```
margin = z × σ = 1.96 × σ
```

**Step 5 — Apply at inference time** (`src/inference.py → get_prediction_interval`)
```
lower = prediction - margin
upper = prediction + margin
```
Lower bound is clamped at 0 (prices can't be negative).

### What's stored in `interval_est.pkl`
```python
{"z_score": 1.96, "residual_std": σ, "pi": 0.95}
```

### Assumptions and limitations

- Assumes residuals are normally distributed (reasonable for this dataset).
- Uses the training residual std (not test) — slightly optimistic. Production systems use a held-out calibration set.
- Constant interval width (homoscedastic) — the interval is the same ±31 lakhs for a ₹40 lakh flat and a ₹120 lakh flat. A log-transform or quantile regression would give a proportional interval.

## 6. How DVC Versions Data and Models

### Core concept

Git tracks code. DVC tracks large binary files (data, models) by replacing them with small pointer files (`.dvc` files) that Git commits, while the actual binary content lives on a remote storage (S3, DagsHub, local folder).

```
Git repo                     DVC remote (S3 / DagsHub)
──────────────────────       ─────────────────────────────
model_features.csv.dvc  ──→  model_features.csv (actual 2 MB file)
model/interval_est.pkl  ──→  interval_est.pkl
dvc.yaml                
dvc.lock (hashes)       
```

### The three pipeline stages

```
Stage: clean
  cmd:  python -m mlops.clean_data
  deps: mlops/clean_data.py, Pune Real Estate Data.xlsx
  outs: data_cleaned.csv

Stage: features
  cmd:  python -m mlops.build_features
  deps: mlops/build_features.py, data_cleaned.csv
  outs: model_features.csv, model_target.npy, model/*.pkl (5 helper artifacts)

Stage: train
  cmd:  python -m mlops.train
  deps: mlops/train.py, mlops/utils.py, model_features.csv, model_target.npy
  params: data.test_size, ridge.alpha, lasso.alpha, etc.
  outs: model/property_price_prediction_voting.sav, model/interval_est.pkl
  metrics: metrics/train_metrics.json
```

### Key DVC commands

```bash
dvc repro              # re-run only stages whose deps changed
dvc status             # show what would be re-run
dvc metrics show       # print metrics/train_metrics.json
dvc metrics diff       # compare metrics between git commits
dvc dag                # ASCII art of the pipeline graph
dvc push               # upload data/models to the remote
dvc pull               # download data/models from the remote
```

### Why DVC over just committing model files to Git

- Git is not designed for binary blobs — a 50 MB `.sav` file bloats the repo forever (Git rewrites history to include every version).
- DVC stores files by content hash (like Git objects) — the remote only stores unique versions.
- `dvc metrics diff main HEAD` shows exactly how R² and RMSE changed between commits.

## 7. What Each mlops/ Script Does

### `mlops/__init__.py`
Auto-loads the project `.env` file (via `python-dotenv`) the moment any `mlops.*` module is imported. This means `DAGSHUB_TOKEN`, `MLFLOW_TRACKING_URI`, etc. are available as `os.environ` variables without any manual `load_dotenv()` call.

### `mlops/utils.py`
The shared utilities module. Everything else imports from here:
- `load_params()` — reads `params.yaml`, returns a dict with safe defaults
- `load_features_and_target()` — reads `model_features.csv` + `model_target.npy`
- `split_data()` — 80/20 train/test split with fixed seed=42
- `score_regressor()` — computes RMSE, MAE, R²
- `build_voting_regressor()` — constructs `VotingRegressor(LR + Ridge + Lasso)`
- `train_voting_regressor()` — fits the model, returns it
- `compute_interval_estimate()` — computes z-score + residual std
- `save_model_artifacts()` — writes `.sav` + `interval_est.pkl`
- `write_metrics_json()` — writes `metrics/train_metrics.json` for DVC

### `mlops/clean_data.py`
DVC stage `clean`. Reads `Pune Real Estate Data.xlsx`, applies data cleaning rules (handle missing values, fix column names, normalise text), writes `data_cleaned.csv`.

### `mlops/build_features.py`
DVC stage `features`. Reads `data_cleaned.csv`, performs:
- NLP feature engineering on the description column (tokenise, POS-tag, count-vectorise)
- Target encoding: map each `sub_area` to its mean price; map amenity score to mean price
- Writes `model_features.csv`, `model_target.npy`, and the five helper `.pkl` files that `inference.py` needs at serving time

### `mlops/train.py`
DVC stage `train`. The "production" trainer — reads `params.yaml`, trains the VotingRegressor, saves `model/property_price_prediction_voting.sav` and `model/interval_est.pkl`, writes `metrics/train_metrics.json`. **No MLflow logging here** — keep the pipeline clean, log separately.

### `mlops/mlflow_train.py`
A fully instrumented training run. Does everything `train.py` does, plus logs parameters, metrics, model artefacts, and diagnostic plots to MLflow. Run this when you want a permanent experiment record.

### `mlops/mlflow_train_v2.py`
An enhanced version of `mlflow_train.py` with additional plots and tagging.

### `mlops/mlflow_sweep.py`
Runs `mlflow_train.py`-style logging once per Ridge alpha value defined in `params.yaml sweep.alphas` (default: 0.01, 0.1, 1, 10, 100, 1000). Each call is one MLflow run. Used to find the optimal regularisation strength.

### `mlops/mlflow_sweep_v2.py`
Enhanced sweep with additional metric logging and model registration.

### `mlops/mlflow_query.py`
Queries the MLflow tracking server, prints a leaderboard of all runs sorted by R², and generates a bar chart of R² vs alpha. Run after `mlflow_sweep.py` to identify the best hyperparameter.

### `mlops/pycaret_benchmark.py` / `_v2.py` / `_v3.py`
Runs PyCaret AutoML to benchmark all sklearn-compatible regressors against the Lab-3 VotingRegressor. Logs results to MLflow. Answers the question: "Could AutoML produce a meaningfully better model?" (Answer: no — the VotingRegressor is competitive with the best AutoML finds on 200 rows.)

### `mlops/dagshub_setup.py`
Helper to configure MLflow and DVC to point at DagsHub instead of local storage. Run `python -m mlops.dagshub_setup --check` to verify credentials and `--print-dvc-cmds` to get the exact commands to add a DagsHub DVC remote.

### `mlops/dvc_init.py`
One-time DVC initialisation script. Equivalent to running `dvc init` + adding a remote + configuring DagsHub credentials.

## 8. How the FastAPI Service Loads Artifacts and Serves Predictions

### Startup sequence (when `uvicorn src.app:app` runs)

```
1. Python imports src.app
2. src.app imports src.inference
3. src.inference executes module-level code:
   a. Downloads NLTK corpora (punkt, stopwords, etc.) — skipped if cached
   b. Loads model         = joblib.load('model/property_price_prediction_voting.sav')
   c. Loads vectorizer    = pickle.load(open('model/count_vectorizer.pkl', 'rb'))
   d. Loads sub_area_map  = pickle.load(open('model/sub_area_price_map.pkl', 'rb'))
   e. Loads amenities_map = pickle.load(open('model/amenities_score_price_map.pkl', 'rb'))
   f. Loads interval_est  = pickle.load(open('model/interval_est.pkl', 'rb'))
   g. Loads feature_names = pickle.load(open('model/all_feature_names.pkl', 'rb'))
4. src.app creates the FastAPI app and registers routes
5. uvicorn starts the HTTP server on port 8000
```

All six artifacts are loaded **once at startup** into module-level globals. Subsequent requests reuse these in-memory objects — no disk I/O per request.

### Request lifecycle for `POST /predict`

```
Client sends JSON:
{
  "property_type": 2, "area": 1000.0, "sub_area": "kothrud",
  "description": "spacious 2bhk with park view",
  "clubhouse": 1, "school": 1, "hospital": 0, "mall": 1,
  "park": 1, "pool": 0, "gym": 1
}
      │
      ▼
FastAPI + Pydantic validates → PropertyInput object
      │
      ▼
src/inference.py → predict_price(data)
  Step 1: Clean description
          "spacious 2bhk park view"  (lowercase, strip punctuation, remove stopwords)
  Step 2: POS-tag tokens
          [("spacious","JJ"), ("2bhk","NN"), ("park","NN"), ("view","NN")]
          noun_count=3, verb_count=0, adj_count=1
  Step 3: Target-encode sub_area
          "kothrud" → sub_area_map["kothrud"] = 65.0 lakhs
  Step 4: Compute amenity score
          sum([1,1,0,1,1,0,1]) = 5
          amenities_map[5] = 74.0 lakhs
  Step 5: Vectorise description
          vectorizer.transform(["spacious 2bhk park view"]) → sparse → dense [0, 1, 0, ...]
  Step 6: Assemble 115-D vector
          [2, 1000.0, 1,1,0,1,1,0,1, 65.0, 5, 74.0, 3,0,1] + [100 text features]
  Step 7: Predict
          model.predict(DataFrame(vector, columns=feature_names)) → [62.3]
  Step 8: Interval
          margin = 1.96 × 16.0 = 31.36
          lower = max(0, 62.3 - 31.36) = 30.94
          upper = 62.3 + 31.36 = 93.66
  Step 9: Return
          {"predicted_price": 62.3, "lower_bound": 30.94,
           "upper_bound": 93.66, "features_used": 115}
```

### Route summary

| Route | Method | Handler | Description |
|---|---|---|---|
| `/health` | GET | `health_check()` | Returns `{"status": "API is healthy and running."}` — used by load balancers and Docker health checks |
| `/model/info` | GET | `model_info()` | Returns model type, vocabulary size, interval margin |
| `/predict` | POST | `predict()` | Full inference pipeline |
| `/docs` | GET | Auto-generated | FastAPI Swagger UI |
| `/redoc` | GET | Auto-generated | ReDoc API documentation |

### CORS configuration

`app.py` sets `allow_origins=["*"]` which allows the HTML file to be opened from any origin (including `file://` on the local filesystem). In production with a custom domain, restrict this to the domain:

```python
# app.py — production hardening (future improvement)
import os
origins = os.getenv("CORS_ORIGINS", "*").split(",")
app.add_middleware(CORSMiddleware, allow_origins=origins, ...)
```

### Why the frontend is static HTML (not React/Vue)

- Zero build step — open `frontend/index.html` directly in a browser
- No Node.js dependency
- Easy to embed in the lab documentation
- For production scale, replace with a proper SPA framework
